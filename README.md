# 朗读插件 —— 流式离线神经音色

给 DeepSeek Harness Web UI 加的「朗读」能力，参考豆包回复语音朗读的交互，并在 1.3.0 起
按「小智」的做法改为**流式合成**：Host 边合成边把 PCM 推给页面，页面用 Web Audio 排期播放，
**第一句还在合成时就开始出声**。

## 功能

- 每条**已完成的助手回复**下方，在自带的复制/分支按钮行里多一个喇叭按钮；点一下朗读，朗读中变成跳动的音量条，再点停止。
- 只朗读回复正文：推理过程、工具调用、代码块、表格、markdown 标记都不会被念出来。
- **流式播放**：不分段等整句，音频分片一到就排进播放队列；多句之间**合成与播放重叠**。
- 设置 → 通用 → 朗读：音色分组（本地快速 / 本地慢速 / 云端）、语速 0.5×–2.0×、试听。
- 同一时间只朗读一条，切换会先停掉上一条（含已排期未播的音频）。
- **自动降级**：没装离线模型、或 Host 不可达时，自动回退到浏览器系统语音，功能不中断。

## 流式是怎么做的

```
Host                                           浏览器
OfflineTts.generateAsync(onProgress)  ──►  ReadableStream
   每产出一片 PCM 就立刻写出                  逐帧解析 DRS1 头 + 长度前缀
   分片：{ uint32 len, int16 samples }  ──►  AudioBufferSource 排到同一条时间轴上
```

实测（Piper 中文模型，一句约 5 秒音频）：**首片音频约在总合成时长的一半处到达**，
所以出声时间从「等整句合成完」提前到「首片到达即可开始」。

多句文本不会串行等待：播放当前句的同时，下一句的合成请求已经发出。

如果运行环境没有 Web Audio（`AudioContext` 不可用），会自动退回整段 WAV 请求，功能不受影响。

## 自动朗读（1.5.0 新增）

会话标题栏右侧多一个**自动朗读开关**（喇叭+播放标记），**按会话单独记忆**：
开着的会话每轮结束自动读，别的会话不受影响。

### 两种模式（设置 → 通用 → 朗读 → 自动朗读）

| 模式 | 行为 |
|---|---|
| **每轮完成**（默认） | 这一轮全部结束后，读最终回复全文。语义清楚，不会读一半。 |
| **边生成边读** | 回复还在生成时，按**完整句子**（`。！？!?\n`）切出来读，半句不读。 |

模式**下一轮生效**：切换不会把正在读的内容腰斩（模式在轮次开始时锁定）。

### 开关与轮次语义（1.5.4 修正）

- **关掉开关立即静音**：不只清标记，还会停掉该会话正在播的自动朗读、清空它的待读队列；
  队列出队时也会再校验会话是否仍开启（关掉瞬间恰好在排队的也会跳过）。
  **手动朗读不受影响** —— 那一次不是开关启动的。
- **只读最新一轮**，绝不回退：新一轮刚开始、文本还是空的时候，**不会**去读上一轮已完成的回复等它。
  旧实现里两个 `continue` 会造成「先读旧的、再读新的」，已删除。
- **打开开关时跳过历史**：`armSession` 会把点击那一刻已完成的历史轮次标记为已读，
  所以不会一开开关就把屏幕上现成的回复读一遍；正在生成的那一轮**不标记**，正常朗读。
- 「已读」记忆在关开关时**故意保留**，否则重新打开会把刚停掉的那条再读一次。

### 实现要点### 实现要点

- 取文本：从 Chat 快照里找当前轮最新的 `assistant-step` / `assistant` 节点，
  `data.status === 'running'` 表示还在生成；`turn-tail.closing.blocks` 是已完成的最终回复。
  只拼 `kind: 'text'` 块，推理和工具调用不会念。
- 防重复：每轮只读一次；流式模式用**字符游标**记录已读到哪里，只读新增部分。
- **排队播放**：音频排队逐条播，不并发。因为开始新朗读会取消当前朗读，
  直接边到边播会把除最后一句外的全部截断。
- 手动朗读某条回复时，自动朗读**让路不打扰**；自动朗读的播放 id 带 `\u0001` 标记区分。
- 会话隔离：队列、游标、已读轮次全部按 sessionId 分键。

> 1.5.0 修复：`createStore.set` 是 patch 合并语义，早先把整个 map 当 patch 传，
> 导致关闭开关后旧 sessionId 以 `false` 形式残留、开关关不掉。现改为把 map 放在单一 key 下。

## 中英文混读（重要）## 中英文混读（重要）

**单语中文模型**（如 Piper 系）词表是拼音，**本身不认识英文单词**。
喂纯英文给它们，引擎会打印 `Ignore OOV 'Hello'` 并把词丢掉，输出近乎静音
（实测纯英文 peak 仅 0.003，纯中文 0.63）。

所以朗读按**语种分段**处理：

| 文本片段 | 用什么读 |
|---|---|
| 中文 | 离线神经音色 |
| 英文单词 / 缩写（`kWh`、`API`、`percent`） | 系统英文音色（如 Microsoft Zira） |
| 数字、空格、标点 | 归入相邻片段，交给对应引擎 |

例：`今天总用电 12340 kWh，比昨天增加了 5 percent。` 会被拆成
`神经:今天总用电 12340` → `系统:kWh` → `神经:比昨天增加了 5` → `系统:percent`。

英文片段两侧的中文标点会被剔除，避免英文音色去念「，」；段与段之间天然有停顿。
如果系统里连英文音色都没有，英文片段会被**跳过**而不是播一段静音。

> 想让英文也用同一副好嗓子，需要换成多语言模型（如 Kokoro multi-lang，`zf_*`/`zm_*` 音色），
> 体积 140 MB 起，是当前模型的 7 倍。

## 音色选择的优先级

- 在设置里**显式选了哪个音色，就用哪个**——选系统音色不会被已安装的离线音色顶掉。
- `自动选择（优先离线音色）`（存储值为空）才会优先用离线模型，没有离线模型时用浏览器自带的系统语音。
- 存储的音色如果已被卸载，会回落到该引擎的默认音色，而不是偷偷换引擎。

> 1.3.2 修复：此前 `resolveVoice` 的判定顺序写反了，只要装了离线音色就抢先返回第一个，
> 导致系统音色单选立即回弹、选不了。同时补上云端音色在下拉里的回显。

## 音色

音色模型放在 `~/.dsh/read-aloud-voices/<音色id>/`，每个目录一个 `plugin.json`：

```json
{
  "id": "my-voice",
  "label": "我的中文男声",
  "description": "中文单语模型，int8 量化，完全离线",
  "language": "zh-CN",
  "license": "CC0",
  "model": { "file": "model.onnx", "tokens": "tokens.txt", "lexicon": "lexicon.txt" },
  "ruleFsts": ["date.fst", "number.fst", "phone.fst"]
}
```

已安装：

| 音色 | 体积 | 授权 | 速度 | 说明 |
|---|---|---|---|---|
| **VITS / Piper** | 约定 20 MB | 见模型卡 | 快 | 单语中文，英文需外挂系统音色 |
| **Matcha 中英混读** | 142 MB | 见包内 README | **很快（RTF≈0.20）** | Matcha+Vocos，自己读中英，16 kHz |

### Matcha 中英混读（1.4.0 新增）

官方「Chinese-English」分类下真正可用的离线模型。实测（同一批句子）：

| 句子 | 单语 Piper | Matcha | 对比 |
|---|---|---|---|
| 纯中文 | RTF 0.74 | **RTF 0.19** | 快 4× |
| 纯英文 | RTF 1.94，**peak 0.003（静音）** | **RTF 0.25，peak 0.860** | 能读了 |
| 中英混合 | RTF 0.75 | **RTF 0.20** | 快 3× |

它是**两段式架构**：声学模型 `model-steps-3.onnx`(72 MB) + 声码器 `vocos-16khz-univ.onnx`(51 MB)，
所以 manifest 里要额外写 `model.vocoder`，且必须 `"kind": "matcha"`。

因为自带中英词典，选中它时**不做语种分段**（`multilingual` 标记），整段一次合成。

代价：采样率只有 **16 kHz**（约电话质量上限），听感会比 22.05 kHz 的 Piper 略闷；只有 1 个说话人。

加新音色 = 解包模型到新目录 + 写一份 `plugin.json`，重启后自动出现在下拉里，不用改代码。
`ruleFsts` 用于把「12340」「2026年10月」这类阿拉伯数字/日期读成中文，缺失时纯按字面推理。

多说话人包（如 Kokoro）还支持 `speakers` 数组，一次列出多个说话人，每项形如
`{ "sid": 3, "label": "Kokoro 女声 01", "language": "zh-CN" }`；`model.kind: "kokoro"` 时走 Kokoro 配置分支。

## 云端音色（预留，默认关闭）

插件自带一条 **OpenAI 兼容**的云端 TTS 通道，默认完全不启用——没有 `cloud.json` 时就只用本地模型。
在 `~/.dsh/read-aloud-voices/` 下建 `cloud.json` 即可开启：

```json
{
  "provider": "openai",
  "baseUrl": "https://api.siliconflow.cn/v1",
  "apiKey": "sk-你的key",
  "model": "FunAudioLLM/CosyVoice2-0.5B",
  "voices": [
    { "id": "FunAudioLLM/CosyVoice2-0.5B:alex", "label": "CosyVoice 男声", "language": "zh-CN" }
  ]
}
```

- 接口按 `POST {baseUrl}/audio/speech` 调用，返回的音频原样回传；
- 云端音色在下拉里单独成组「云端音色（需联网）」，id 内部以 `cloud:` 前缀区分；
- 失败会返回结构化的 `read-aloud/cloud-failed` / `read-aloud/cloud-network` 错误，不影响本地音色；
- `apiKey` 只留在 Host 侧，`/voices` 响应里不含它。

**为什么默认不做成小智那样的 EdgeTTS**：实测本机访问微软合成端点
（`speech.platform.bing.com/.../edge/v1`）连续返回 **403 Forbidden**，而音色列表接口是 200；
即微软已在合成通道加了鉴权，`edge_tts` 那套公开调用在本网络不可用。
火山引擎双向流式（小智 👍 推荐的方案）需要专用二进制协议 + appid/access_token，
本插件预留了位置但未实现，目前只落地了 OpenAI 兼容这一种通用形态。

## 架构

```
浏览器（client.js）                    Host（index.js）
─────────────────                      ─────────────────
喇叭按钮 / 设置行
  │ 选音色、切句
  ├─ 神经音色 ──POST /api/dsh-read-aloud/speech──► OfflineTts 合成 WAV
  │                 { text, voice, rate }            （sherpa-onnx，int8 VITS）
  │  ◄──────────── audio/wav ──────────┘
  │  Audio() 播放 + 预取下一句
  │
  └─ 系统音色 ── speechSynthesis（浏览器内置，离线兜底）
```

Host 侧要点：

- `sherpa-onnx-node` **直接复用 DSH 安装目录里自带的副本**（语音输入功能用的就是它），插件不额外引入依赖。
- Electron 里合成必须传 `enableExternalBuffer: false`，否则报 `External buffers are not allowed`。这是本插件踩到的关键坑。
- 模型首次使用时加载（约 2 秒），之后常驻；同一音色的合成请求串行排队（原生句柄不可重入）。
- 合成结果按 `音色+语速+文本` 缓存 10 分钟，最多 32 条。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/dsh-read-aloud/voices` | 已安装音色列表 + 引擎状态 |
| POST | `/api/dsh-read-aloud/speech` | `{ text, voice, rate }` → `audio/wav` |

错误码：`400` 空文本/非法 JSON、`404` 音色不存在、`413` 超过 6000 字、`503` 引擎不可用、`500` 合成失败。

## 设置行布局

设置面板固定 800px，扣掉侧栏 188px 与左右内边距，内容区只有 **564px**。
所以这一行是上下两段：标题与说明占整行，控件在下方**同一行**并排（音色 168 + 语速 88 + 读数 34 + 试听贴右，实测约 444px）。

## 已知边界

- 首次朗读某个音色会有约 2 秒模型加载时间，之后约 0.3–0.5 秒出首句。
- 音色质量取决于模型；int8 量化比 fp16 略差但体积小 4 倍。
- **模型授权由所选模型包决定**，商用前请逐个核对模型卡。部分中文模型的训练数据集带非商用限制（例如基于 BZNSYP 的模型），选型时务必确认。
- 没有浏览器自动化通道，实际出声效果需人工确认。

## 可选：系统音色补充

Windows OneCore 里还有 Kangkang（男）、Yaoyao（女）等音色，但浏览器 `getVoices()` 读不到（Chromium 只桥接 SAPI5）。
把它们注册成 SAPI5 语音可以多出几个系统音色，但需要改注册表；既然已有离线神经音色，一般没必要。
